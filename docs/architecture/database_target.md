# LedgerPulse target database specification

**Status** — Proposed for review. This specification follows the repository audit and defines the launch schema and accounting boundaries. The decisions at the end are gates for historical conversion and feature behavior. See the [ERD](database_erd.md), [migration plan](database_migration_plan.md) and [source audit](database_audit.md).

## Design conventions

- PostgreSQL is authoritative for accepted writes. Drift holds confirmed replicas and pending local work. Supabase Auth manages credentials and session identity exclusively.
- Unless stated otherwise, fields are required. `?` denotes nullable. `uuid` IDs are generated before offline creation and survive retries. `timestamptz` is a UTC instant and `date` is a business calendar date. Use exact `numeric(20,6)` for quantities and `numeric(9,6)` for percentages, subject to source precision checks. Money uses signed PostgreSQL `bigint` minor units. Nonnegative fields use explicit checks. Transmit 64-bit monetary values and sync counters losslessly as decimal strings in JSON. Use a supported currency whitelist with an explicit minor-unit exponent.
- **Managed fields (M)** means server `created_at timestamptz`, `updated_at timestamptz`, and `revision bigint` initialized to 1 and incremented on each accepted change. **Tombstone (T)** means `deleted_at timestamptz?`, set and cleared through controlled lifecycle operations only. Immutable facts use creation metadata alone. A change to a document child also increments the parent document revision.
- Every workspace child belongs to the relevant subtype, directly or through a scoped parent. Every relationship between workspace-owned records uses a composite FK `(workspace_id, referenced_id)` to a unique `(workspace_id, id)` key on the target. A nullable reference leaves only the referenced ID nullable. Child IDs are globally unique and immutable. Same-scope FK columns get supporting indexes unless an existing index covers the prefix.
- Default FK delete behavior is restrictive. Archive reference data used by history. Retain sync tombstones through the supported offline window and retained dependencies. Scheduled hard purge, where permitted, is privileged and retains audit and accounting obligations. No cascading removal of posted or audit history from account/workspace deletion.
- Checked code fields use closed value sets. Published legacy enum values need an explicit conversion dictionary. Existing reusable domain checks can be carried forward where they match observed behavior. Workflow-dependent checks and cross-row invariants belong in controlled transactions, supported by database constraints.

Create the workspace and subtype in one transaction. A deferrable, initially deferred database constraint trigger on the parent and both subtype tables verifies exactly one matching subtype for surviving workspaces at commit. Composite subtype FKs enforce type on every insert. All privileged subtype/lifecycle writes lock the same workspace row, including removal paths. Ordinary clients have no independent subtype delete or owner-update permission. Lifecycle operations use a revision check and return explicit outcomes. Archived workspaces are read-only. Deleted workspaces expose their lifecycle marker through owner discovery and have financial content available only after controlled restoration or authorized recovery. Retention and account closure remain rollout gates.

### Accounting contract

Vouchers record documents and conversion history. Journals represent postings, including operations without a sales or purchase document. Journal lines are the single authority for account and party monetary movements. The party ledger is a scoped projection of control-account lines plus voucher/journal metadata. The prior entry table duplicates many posting facts and currently carries distinct UI metadata. Move proven metadata to its authoritative document or journal. The party projection selects control-account legs because historical entry posting tagged both sides with the same party. Never sum all party-tagged lines. Inventory movement is a quantity fact with its own source trace. [Standalone entry posting](../../lib/data/local/drift_entries_mixin.dart#L127), [voucher posting](../../lib/data/accounting/voucher_posting_engine.dart#L386), [voucher line model](../../lib/data/models/voucher_model.dart#L176)

- Post through one controlled operation that locks the workspace and relevant draft, checks expected revision and lifecycle, validates numbers, references and accounting rules, then commits the document, balanced journal/lines, applicable stock movements, audit and sync batch together. Direct journals require balancing and authorization as well. Drafts, orders and estimates do not affect balances. A posted journal has at least two lines and total debits equal total credits. Validate at the database transaction boundary, with an independent deferred invariant covering affected journals. Ordinary clients cannot mutate posted journals or lines.
- Reversal appends an equal and opposite journal retaining account/party dimensions and any corresponding inverse stock movements. Preserve original rows. Effective-date reporting includes both at their own dates. Posted correction uses an atomic reversal and replacement workflow. A reversal does not authorize reuse of the original document number. Reporting may display a voided state while retaining both posted facts.
- General ledger balance derives from debit/credit movement with account presentation sign. Receivable/payable display derives from control accounts and product display rules. Opening entries are explicit balanced postings. Document totals, tax snapshots and stock extended costs may preserve distinct historical document facts. Client current/running balances are projections.

## Security and synchronized writes

| Surface | Launch access |
| --- | --- |
| Auth and `public.users` | SDK manages Auth. Authenticated owner reads own personal row, and a self-update command accepts only editable personal fields. No anonymous access to application rows. |
| Workspace root and profiles | RLS on each using `auth.uid()` and verified owner resolved from stored workspace. Owner discovery can read lifecycle markers. Typed profiles require read-eligible lifecycle. Authenticated client creates and changes workspaces through controlled functions. |
| Memberships | Owner may inspect own workspace roster if displayed. Delegated rows convey zero access at launch. No client membership writes. Later sharing needs permission-by-action design, verified active membership, revocation and explicit rollout. |
| Expense and Ledger rows | RLS SELECT is scoped to owner and allowed lifecycle. Deny raw INSERT/UPDATE/DELETE via grants and policies. Commands resolve row scope from persisted targets and validate all input references. Archive/deleted lifecycle restricts mutation. Reports respect underlying RLS and are exposed only via invoker-safe views or authorized functions. |
| `private.workspace_commits` | Internal writes only. Schema excluded from Data API, no client table grants, and no direct access under RLS. Authorized pull and command functions expose minimal outcomes. |
| `storage.objects` | Private bucket. Owner/path policy and verified object-to-workspace relationship apply to reads and writes. Account avatars are UID scoped. Receipt, logo and signature keys are workspace scoped. Commands validate expected domain and object key. Upload staging and unreferenced object cleanup run separately from accounting commits. |

Controlled functions derive identity from Auth context, reject unknown commands, authorize every action from stored workspace and target state, use explicitly qualified relations and a fixed trusted search path, and grant execution narrowly. The mutation transaction also validates lifecycle and target revisions. No authorization derives from editable Auth metadata, legacy profile role, request owner ID or a device claim. Where future sharing adds read roles, account/banking and signing metadata need column-level permission decisions. Removing entitlement must invalidate workspace access before replaying prior operation receipts.

### Commit feed and idempotency

`private.workspace_commits` exists to retain one accepted operation and its atomic change batch. Columns are `workspace_id uuid` FK to workspace, `sequence bigint`, `operation_id uuid`, `actor_user_id uuid?` FK to users subject to retention, `command_kind text`, `protocol_version integer`, `request_hash bytea`, `committed_at timestamptz`, and `changes jsonb?`. PK `(workspace_id, sequence)`, unique `(workspace_id, operation_id)`. The feed payload is a bounded versioned wire envelope of allowlisted row snapshots and removals. It is transport history. Current relational tables own the data. Retain hash, actor binding and sequence for safe replay when payloads age out, and confirm retention capacity before any pruning. Retries after payload expiry receive the accepted sequence and resnapshot when required.

1. A device generates stable record IDs and an operation UUID. Its Drift transaction stores pending display effects and the immutable command envelope with expected revisions. Retries reuse the UUID and payload. Editing an operation already eligible to send creates a new dependent operation.
2. Server resolves Auth and persisted scope, then locks the workspace and revalidates authorization under that lock. Check the receipt under the same lock. A matching actor and canonical payload hash returns the original result, and mismatched operation-ID reuse is rejected. For a new operation, compare expected revisions before writing. An unaccepted conflict returns a structured outcome with current revisions scoped to the caller. Concurrent creation converges on the unique workspace UUID, then verifies owner and accepted receipt before replay.
3. Each accepted operation increments `workspaces.sync_head` under the same row lock and records one ordered batch atomically. Concurrent transactions cannot commit out of order inside a workspace. (workspace, sequence) is the cursor. A device applies each complete batch and advances the cursor in one Drift transaction. Pagination is across batches, with size limits on accepted commands and no partial application. A device may retry a pull safely.
4. Use a consistent snapshot with a captured head for initial sync and expired cursors. Capture rows and head from one database snapshot and materialize or stream it as one snapshot even when transport is paginated. Pull authorized batches after that head. An expired cursor or protocol epoch mismatch returns an explicit resnapshot outcome. Never skip a pruned batch and advance the cursor. Scope discovery uses the authoritative owner list, including lifecycle markers. Loss of access clears confirmed cache and preserves pending work in an inaccessible recovery queue subject to retention policy. Keep unsent edits separate from confirmed data and rebase explicitly after resnapshot.
5. Personal-profile writes use a revision-checked complete replacement of editable fields and a self-row refresh. A retry with the same normalized desired state can return the current revision as a no-op. This independent account row needs no workspace feed. Workspace receipt replay is the contract for financial and workspace mutations.
6. Multiple devices share server identity and workspace sequences. Drift stores retry status, last applied sequence, pending command dependencies, conflict state and local selection. Supabase sessions supply authentication. A server device registry and a server outbox have no launch dependency.

## Decisions at review

- Finance owners must approve mappings for ambiguous legacy party entries, AR/AP signs, historical opening postings, unusual voucher or journal cardinality, tax rounding, invoice numbering, and corrections in closed periods. Preserve original data and exclude ambiguous cases from activation until reconciled. Non-document Ledger credit/payment workflows retain proven metadata without introducing a parallel mutable subledger.
- Confirm whether inventory costing posts to the general ledger for each supported movement, stock precision, cost method, and negative-stock policy. A stock movement may omit journal association for explicitly approved quantity-only adjustments.
- Agree on budget rollover, concurrent/overlapping limits and category hierarchy reporting. Approve recurring month-end/time-zone behavior and scheduler ownership. Each accepted occurrence and advancement is one idempotent transaction. An offline device can propose it; no device can independently advance the canonical schedule.
- Confirm the supported currency set, minor-unit interpretation of legacy values and handling of mixed wallet currencies. Keep one currency per workspace at launch conditional on legacy reconciliation.
- Confirm archive/restore/purge and receipt retention, effective date conversion, offline support window, and which existing per-business module flags represent persisted settings. If module controls must remain configurable, prefer a typed per-workspace relation with checked module codes after the active flags are inventoried. There is no placeholder settings JSON.
- The launch storage shape preserves one receipt per transaction, voucher or standalone activity as used by current paths. Existing attachment rows and file references must be inventoried. Proven multiple-attachment requirements would require a scoped child relation before those workspaces cut over.
